2. Product Summary
WarpTalk is a real-time multilingual communication platform for B2B meetings. It lets a host create a translation room, participants join with speak/listen languages, the system routes live audio through STT, translation, TTS, and AI assistant workers, then persists transcripts, translations, summaries, artifacts, feedback, notifications, and usage billing.


The current implementation is a microservice system:


* Gateway: public API entry point through YARP and SignalR hubs.
* Auth Service: users, JWT, refresh tokens, Google login, profile.
* TranslationRoom Service: room lifecycle, participants, language policy, audio routes, artifacts, feedback.
* Meeting Service: LiveKit joining, meeting room records, chat, chat moderation, meeting history.
* Transcript Service: transcript query APIs, glossary APIs, Redis persistence consumer for STT/translation results.
* Notification Service: user notifications, preferences, admin notifications.
* Billing Service: plans, subscriptions, credits, transaction history, idempotent credit operations.
* AI Workers: Python Redis Streams workers for STT, translation, TTS, voice cloning, summary/action items.
* Infrastructure: PostgreSQL, PgBouncer, Redis, COTURN, Prometheus, Grafana, Seq, backups.

Gateway security and performance:


* JWT Bearer auth validates issuer, audience, lifetime, signing key.
* SignalR tokens are accepted through ?access_token=... only for /hubs.
* Global rate limit: 100 requests/minute per remote IP or host.
* Login rate policy exists: 5 requests/minute, but verify it is actually applied to auth routes before production.
* Notification inbox route has InboxPolicy: 30 requests/minute.
* SignalR maximum receive size: 128 KB.
* Security headers include X-Content-Type-Options, X-Frame-Options, X-XSS-Protection, Referrer-Policy.

	7.2 Important Tables
Auth:


* auth.users: email, password hash, Google ID, profile, lockout, email verification, audit timestamps.
* auth.refresh_tokens: hashed refresh tokens, device, IP, expiry, revocation.
* auth.roles, auth.permissions, auth.role_permissions, auth.user_roles.
* auth.user_settings: default speak/listen language, voice clone toggle, mic suppression, recording/summary defaults, UI accessibility settings.


Translation room:


* translation_room.translation_rooms: workspace, host, title, code, lifecycle status, source/target languages, settings, timestamps.
* translation_room.translation_room_participants: participant user/display name, role, speak/listen languages, status, audio and voice clone flags.
* translation_room.translation_room_audio_routes: source participant, target participant, language pair, route status, stream ID, voice clone flag.
* translation_room.translation_room_artifacts: post-room artifacts, file info, consent and retention metadata.
* translation_room.translation_room_feedback: user ratings and comments.


Meeting:


* meeting.meeting_rooms: maps translation_room_id to provider room name and LiveKit lifecycle.
* meeting.meeting_participants: provider identity and join/leave metadata.
* meeting.meeting_tracks: media tracks.
* Chat entities exist in domain (MeetingChatMessage, translations, moderation, assistant requests), but current MeetingDbContext.cs reviewed does not show mappings for those chat tables. This is a current implementation gap to verify before relying on chat persistence.


Transcript:


* transcript.transcripts: one logical transcript per translation room and version, status, source language, counters.
* transcript.transcript_segments: ordered original STT segments.
* transcript.transcript_translations: translated text per segment and target language.
* transcript.transcript_corrections: human corrections and retranslation flags.
* transcript.transcript_exports: export file metadata.
* transcript.glossaries, transcript.glossary_terms: workspace terminology.


Billing:


* billing.plans: plan name, price, credits per month.
* billing.subscriptions: one active subscription per workspace via unique partial index.
* billing.credit_transactions: top-up and consumption ledger.
* billing.transactions: payment transaction records.
* billing.idempotency_records: idempotent operation cache by key and operation.


Notification:


* notification.notification_messages: user-facing notifications.
* notification.notification_preferences: channel preferences.
* notification.admin_notifications: admin-created broadcasts.
7.3 Data Integrity Rules
* Every major table uses UUID IDs.
* Domain schemas intentionally avoid physical FKs to external service-owned entities in several DbContexts. Example: Transcript stores workspace_id and translation_room_id as external IDs and validates access via gRPC.
* Billing enforces one active subscription per workspace.
* Transcript enforces unique (translation_room_id, version) and unique (transcript_id, sequence_order).
* Transcript translations should enforce unique (segment_id, target_language).
* Translation room code should be unique across non-terminal rooms.
* Soft deletion appears via deleted_at in many tables; queries must filter deleted rows.
7.4 Database Risks And Required Cleanup
Current mismatches to resolve:


* Infrastructure init-db.sql uses schemas including subscription, while Billing service uses schema billing.
* Some SQL references look stale, for example old auth/workspace location and rename migrations.
* AuthDbContext still has workspace entities under auth, while infrastructure migrated workspace tables to workspace.
* TranscriptDbContext.OnConfiguring contains a scaffolded local connection string warning. Production must rely on configuration only.
* Meeting chat domain and repositories exist, but reviewed DbContext mapping does not include MeetingChatMessage and related chat tables.

	9.2 Main Rules
* Register lowercases and trims email.
* Duplicate email returns EmailExists.
* Register assigns default role "member" in token response, but confirm role persistence/seed.
* Login:
   * inactive user is rejected.
   * 5 failed password attempts locks account for 15 minutes.
   * successful login resets failed attempts and lock status.
   * refresh token is hashed before storage.
* Refresh:
   * old token is revoked.
   * new access and refresh token are issued.
   * expired/revoked/missing token is rejected.
* Google login:
   * verifies Google token.
   * creates user if missing.
   * links Google ID to existing email if needed.
* Change password:
   * Google-only users with empty password hash can set a password.
9.3 Happy Cases
* User registers, receives access token, refresh token, expiry, user profile.
* User logs in with valid password and active account.
* User refreshes token once; old refresh token cannot be reused.
* User updates profile fields and receives updated profile.
9.4 Unhappy Cases
* Duplicate email registration.
* Wrong password increments failed count.
* Account locked after 5 failed attempts.
* Google token invalid.
* Refresh token reused after rotation.
* Authenticated user has missing NameIdentifier claim.

10.4 Create Room Mainflow
Input:


* workspaceId
* title
* description
* translationRoomType
* maxParticipants
* sourceLanguage
* targetLanguages
* settings.requiresApproval
* settings.artifactAccess
* scheduledAt


Flow:


1. Extract host ID from JWT.
2. If sourceLanguage or targetLanguages are missing, load defaults from auth.user_settings equivalent repository:
   * default speak language -> source
   * default listen language -> first target
3. Validate source language exists and is supported.
4. Validate target languages exist and are supported.
5. Determine initial status:
   * scheduled room -> SCHEDULED
   * instant room -> WAITING
6. Generate unique 12-character room code.
7. Persist room.
8. Return TranslationRoomDto.


Happy case:


* Host creates instant room with source vi-VN, targets en-US, status becomes WAITING, room code is returned.


Unhappy cases:


* Missing source and no user default.
* Unsupported source or target language.
* scheduledAt in past.
* maxParticipants <= 0.
* Room code collision loops until unique.
* Database error.
10.5 Join Room Mainflow
Input:


* translationRoomCode
* displayName
* speakLanguage
* listenLanguage


Flow:


1. Extract user ID from JWT.
2. Find non-terminal room by code.
3. Load user default languages if speak/listen omitted.
4. Validate participant languages against room policy:
   * speak/listen must be supported.
   * language must match source or allowed target policy.
5. Upsert participant record by (roomId, userId).
6. If participant was KICKED, reject permanently.
7. Determine approval behavior:
   * host joins as connected.
   * if requiresApproval, non-host participant status is WAITING.
   * otherwise participant can become CONNECTED.
8. Return room + participant.


Happy cases:


* Host joins own room and becomes connected.
* Participant joins room and waits for approval.
* Participant rejoins and updates language preferences.


Unhappy cases:


* Invalid room code.
* Terminal room code.
* Kicked participant attempts rejoin.
* Unsupported language.
* Display name missing or too long.
* Room full, if max participant enforcement is completed.
10.6 Waiting Room And Participant Management
Host actions:


* Admit participant: WAITING -> CONNECTED.
* Kick participant: any non-host participant -> KICKED.
* Toggle translation audio: changes IsTranslationAudioEnabled, not microphone mute.


Participant action:


* Leave room: participant -> LEFT.


Authorization:


* Only host can admit, kick, manage participant translated audio.
* Host cannot kick self.
* Non-host can list participants only if connected or if policy permits.
10.7 Audio Routing
Purpose:


* For every speaker/listener pair, generate route if source language differs from target language.
* Same-language pairs should bypass machine translation.


Route statuses:


* PENDING
* READY
* BROADCASTING
* PAUSED
* SPEECH_DELAYED
* TRANSLATION_DELAYED
* VOICE_DELAYED
* STANDARD_VOICE
* CAPTION_ONLY
* ENDING
* SAVING_OUTPUTS
* SAVE_FAILED
* COMPLETED


Generate route flow:


1. Load room.
2. Validate room source/target policy exists.
3. Load participants.
4. Build full mesh for all participant pairs.
5. Skip same source/target language pairs.
6. Update stale routes.
7. Add missing routes.
8. Remove obsolete routes for participants no longer active.
9. Publish route update to Redis.


Runtime events:


* Session start/end/pause/resume triggers audio route state machine.
* Telemetry can degrade route status:
   * STT degraded -> speech delay.
   * translation degraded -> translation delay.
   * TTS degraded -> voice delay or text-only mode.
   * voice clone unavailable -> fallback to standard voice.
10.8 Artifacts And Feedback
Artifacts:


* Transcript exports, summary exports, debug logs, optional recordings, audio samples.
* Access level is controlled by room settings and artifact metadata.
* Consent may be required for raw audio/video artifacts.
* Retention time must be enforced by cleanup worker or scheduled process.


Feedback:


* User submits 1-5 overall rating.
* Optional quality dimensions:
   * translation quality
   * audio quality
   * voice clone quality
   * AI summary quality
* One feedback per (roomId, userId) should be enforced.

12.4 AI Provider Normalization
Different AI providers must be normalized at the worker boundary. UI and backend must never depend on provider-specific raw output.


Required normalization rules:


* All IDs are UUID strings.
* Language codes use one platform standard. Recommended: BCP-47 (vi-VN, en-US) at API/UI level; worker adapters may map to model-specific codes internally.
* Text fields are always UTF-8 strings.
* Confidence is decimal 0-1 where provider supports it; otherwise use null or omit and set confidence_source = "not_supported".
* Latency is measured in milliseconds from original audio chunk timestamp.
* Each message includes model metadata:
   * model_provider
   * model_name
   * model_version
   * schema_version
* Workers must implement fallback without changing the output schema.
* Empty final chunks are allowed only to signal finalization and must include is_final_chunk = 1.
12.5 Current Contract Mismatches To Fix
These are observed in source and should be treated as blockers for reliable realtime persistence:


1. Gateway PublishAudioChunkAsync writes field translation_room_id, but Python AudioChunkMessage.from_redis() requires meeting_id.
2. Gateway writes stream audio:chunks:{translationRoomId} while STTWorker.input_stream is audio:chunks unless stream discovery/pattern logic is changed.
3. Python BaseWorker.publish("stt:results", meeting_id, ...) writes stt:results:{meeting_id}, but Gateway AiResultConsumerService consumes stt:results without suffix.
4. Translation Worker reads target language from meeting:{meeting_id}:languages, but Gateway stores it under translationRoom:{translationRoomId}:languages.
5. Transcript persistence for translations expects translation_id, text, target_language, model, while Translation Worker emits segment_id, translated_text, target_lang.
6. Gateway uses meeting_id field to infer translationRoomId; canonical naming should be room_id or consistently preserve meeting_id until all services are migrated.


Recommended migration:


* Phase 1: add backward-compatible readers that accept both old and new field names.
* Phase 2: change producers to canonical fields.
* Phase 3: update tests for every stream schema.
* Phase 4: remove old names after one release.
12.6 Latency Budget
Target realtime experience:


Stage
	Target
	Client chunk size
	1s audio chunks

	< 50 ms

	150-500 ms depending model/GPU
	Translation

17. Non-Functional Requirements
17.1 Performance
* Gateway HTTP p95 target: < 300 ms for simple reads.
* Room create/join p95 target: < 800 ms.
* SignalR transcript broadcast target: < 2s from audio chunk start.
* Translated audio target: < 3s preferred, < 5s acceptable.
* Transcript consumer throughput target from plan: 500+ segments/second.
* Redis stream max length must prevent unbounded memory growth.
17.2 Reliability
* Redis consumers must be idempotent.
* Redis stream messages must be acked only after successful processing or after deliberate discard of invalid payload.
* AI worker crash should not end a room; it should degrade the AI/audio path.
* Billing should not double-charge on retries.
* Live meeting join can succeed even if AI trigger publish fails, but UI must show AI degraded state if known.
17.3 Security
* JWT validation on all protected APIs and hubs.
* Role-based policies for admin/internal/workspace owner routes.
* Refresh tokens stored only as hashes.
* gRPC internal calls require internal secret in production.
* CORS must be strict in production.
* Do not expose dev/test endpoints in production.
* Raw audio/video artifacts require consent and retention policy.
17.4 Privacy And Compliance
* Consent records are required for voice cloning and raw audio/video storage.
* Artifacts must carry retention metadata.
* Access logs should exist for sensitive artifact access.
* Workspace document sensitivity/confidentiality should guide AI eligibility.
* Users should be able to request data deletion in future privacy module.
17.5 Observability
* Every request should have a correlation/request ID.
* Logs must include user ID, workspace ID, room ID when available.
* AI telemetry should publish worker type, room ID, latency, timestamp.
* Dashboards should include:
   * room lifecycle errors
   * SignalR connection counts
   * Redis stream lag
   * STT/translation/TTS latency
   * billing credit consume errors
   * gRPC failure rates

18. Meeting Mainflows For UI
18.1 Host Creates Instant Room
1. Host opens /rooms or host dashboard.
2. Host clicks create room.
3. UI collects title, description, source language, target languages, max participants, approval setting, artifact access.
4. UI calls POST /api/v1/translation-rooms.
5. Backend returns room code and status WAITING.
6. UI navigates to /rooms/{id} or /rooms/{id}/setup.
7. Host copies invite link/code.


UI states:


* Loading submit.
* Validation errors inline.
* Success state with room code.
* Failure state for unsupported language or auth expired.
18.2 Participant Joins By Code
1. Participant opens /join.
2. Enters room code, display name, speak language, listen language.
3. UI calls POST /api/v1/translation-rooms/join.
4. If participant is WAITING, UI navigates to /rooms/{id}/waiting.
5. If participant is CONNECTED, UI navigates to /rooms/{id}/setup or live room.
6. Host sees waiting participant and admits.


Unhappy UI states:


* Invalid code.
* Room ended/cancelled/expired.
* Kicked participant.
* Language unsupported.
* Waiting too long; allow refresh/leave.
18.3 Host Starts Meeting
1. Host sees room status WAITING.
2. Host confirms participants/readiness.
3. UI calls POST /api/v1/translation-rooms/{id}/start.
4. Backend sets IN_PROGRESS and triggers audio routing state machine.
5. UI calls POST /api/v1/meetings/rooms/{translationRoomId}/join.
6. Meeting Service returns LiveKit token.
7. UI connects to LiveKit and /hubs/translation-room.
8. UI starts audio capture and sends chunks.


Unhappy UI states:


* Non-host tries to start.
* Room already ended/cancelled.
* LiveKit token generation failed.
* SignalR connection failed.
* Browser mic permission denied.
18.4 Live Realtime Translation
1. UI captures audio chunks, base64 encodes, calls hub SendAudioChunk.
2. Gateway writes Redis stream.
3. STT produces transcript.
4. Gateway broadcasts TranscriptSegmentReceived.
5. Translation worker produces translated text.
6. Gateway broadcasts TranslationTextReceived.
7. TTS worker produces audio.
8. Gateway broadcasts TranslatedAudioReceived.
9. UI renders:
   * original caption
   * translated caption
   * playback translated audio if enabled
   * route/AI degraded indicators


UI controls:


* Mute/unmute local mic.
* Toggle translated audio.
* Change listen language before or during supported states.
* Show participant list.
* Show live transcript panel.
* Show AI status.
18.5 Pause/Resume
Pause:


1. Host calls POST /pause.
2. Backend sets room PAUSED.
3. Route event tells workers to skip processing room.
4. UI stops or buffers audio sending depending product choice.


Resume:


1. Host calls POST /resume.
2. Backend sets room IN_PROGRESS.
3. Route event resumes workers.
4. UI resumes audio capture.
18.6 End Meeting And Artifacts
1. Host calls POST /end.
2. Backend sets ENDED, stores ended time and duration.
3. Participants move to DISCONNECTED.
4. Audio route state machine gets session_ends.
5. Transcript finalization and AI summary generation should be triggered.
6. UI navigates to /rooms/{id}/ended.
7. UI polls/streams artifact statuses.
8. When ready, UI shows /rooms/{id}/artifacts.
9. User submits feedback.


Artifact states:


* queued
* processing
* ready
* failed
* consent_required
* expired

20. Current Limitations
High priority:


* Redis stream and field contracts are inconsistent between Gateway, AI workers, and Transcript consumer.
* Gateway does not currently route Billing in reviewed appsettings.json.
* Billing schema name differs from infrastructure init SQL (billing vs subscription).
* Meeting chat persistence mapping must be verified.
* Response contracts are inconsistent across services.
* Workspace service is referenced in infrastructure but not present in reviewed backend source.
* Full RBAC is not enforced in web middleware.
* Some dev/test endpoints exist and should be disabled in production.


Medium priority:


* Transcript access returns Forbid() without typed error body in some endpoints.
* Several endpoints return raw strings or anonymous errors.
* Some comments and README encoding are garbled, suggesting file encoding cleanup is needed.
* AI assistant summary trigger is a marker text __MEETING_END__; production should use explicit system event.
* Voice consent tables exist in DB design but are not wired end-to-end.
* Artifact retention and deletion workers are only partially visible.


Low priority:


* Web service adapters normalize backend status casing; backend should standardize casing.
* Web endpoints include some transcript start/finalize/audio routes not seen in reviewed Transcript controllers.
* Some room type values in web (one_to_one, group, webinar, b2b_virtual_mic) exceed backend enum (INSTANT, SCHEDULED).

22. Quality Control Checklist
Before merging any backend feature:


* Endpoint has request validation.
* Endpoint returns typed success and typed error.
* Auth/role policy is explicit.
* Pagination is bounded.
* Logs include operation and entity IDs.
* Tests cover happy case and at least one unhappy case.
* DB migrations are reversible or have safe rollback notes.
* Idempotency is added for retry-prone operations.
* Web API adapter/types updated if contract changed.
* Docs updated in this file.


Before releasing AI/realtime changes:


* Redis stream key and field names match canonical schema.
* Gateway, worker, Transcript consumer contract tests pass.
* Backward-compatible aliases exist for one release if renaming fields.
* Latency telemetry is emitted.
* Fallback mode is tested.
* Dead-letter or retry strategy exists.
* Workers handle pause/resume/end room events.


Before releasing database changes:


* Migration applies to empty DB.
* Migration applies to existing DB.
* Indexes cover expected filters/joins.
* FK ownership is deliberate and documented.
* Enum values match C# and TypeScript.
* Rollback or forward-fix plan exists.


Before releasing UI changes:


* UI route maps to documented endpoint.
* Loading, empty, error, success states exist.
* Auth expired state redirects safely.
* Participant and host see role-appropriate controls.
* Status casing is normalized.
* Realtime disconnect/reconnect is handled.
* Mobile layout fits controls and text.
