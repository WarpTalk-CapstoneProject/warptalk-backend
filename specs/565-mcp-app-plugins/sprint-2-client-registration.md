## 0. Sprint shape

Full three-rung ladder including CIMD, plus the thin tool-gateway slice that makes it
demonstrable. The sprint is done when someone can install a real remote MCP server, connect it,
see its tool list, and have WarpBot call a tool.

**This product has exactly two gates on plugin tool use, both already shipped, and this sprint
changes neither.**

1. **Workspace level — the `AllowAnyPlugins` flag the workspace owner sets.** Kept as is.
   FR-565-015, switch at `settings/page.tsx:685` (owner/admin, default `true`), enforced in
   `McpToolOrchestrator` on **both** paths — `ListAvailableToolsAsync:36` and `ExecuteAsync:66` —
   through `IWorkspacePluginPolicyClient` over gRPC to WorkspaceService.
2. **Per-write — the confirmation token from T038**, which asks the user before any write tool
   executes.

**Invariant the new code must preserve:** the workspace gate lives in `McpToolOrchestrator`,
*above* the gateway. `McpToolGateway` (T071) plugs in *below* it, so the policy applies to
`kind='mcp'` for free — as long as nothing routes execution around the orchestrator. T062A tests
exactly that.

`ListToolsAsync` is the one exception, and deliberately: it runs at **connect** time to populate
`tools_json`, and connecting is personal and workspace-independent. Do not add a policy check
there — the gate belongs at list and execute time, where a user is actually in a workspace.

What does **not** exist is a *per-tool* approval: no table, column, service, endpoint, or UI, and
none planned. T063 deletes the two comments in the tree that imply otherwise.

### Standing rule: `Plugin.cs` and `AssistantDbContext.cs` stay raw scaffold output

Both files are generated by `dotnet ef dbcontext scaffold` and must stay reproducible by re-running
it. Adding a column means: write the migration, re-scaffold (or hand-apply the exact shape scaffold
would produce), and nothing more.

In the entity that means **no XML doc comments, no attributes, and no initializers beyond what
scaffold emits** — `= null!;` for a non-nullable string, nothing for a nullable one. A property
whose column has a database default still gets `= null!;`; the default belongs to the database and
to the DbContext mapping, not to a C# initializer. Documentation and defaults live where the logic
lives: `PluginConstants` for the vocabulary, the migration for the column semantics, the service
layer for behaviour.

The test of the rule is that **re-running scaffold is a no-op**. Adding scaffold-shaped mappings
for new columns to `AssistantDbContext.cs` is therefore fine — regeneration produces the same
lines. Anything scaffold would *not* produce belongs in a partial file instead; the class is
already `partial` and calls `OnModelCreatingPartial`, though no `.partial.cs` exists in this
service yet.

One pre-existing deviation is left as found rather than propagated: `AssistantDbContext` writes
`HasDefaultValue(PluginConstants.PluginKind.Native)` where scaffold emits the literal `"native"`,
so a clean re-scaffold silently reverts it. `oauth_client_source` is mapped with the literal
`"unresolved"` to keep regeneration a no-op. If the constant style is the one you want, move both
into a `.partial.cs` — do not spread it further through the generated file.

## 1. Why this sprint exists

`20260828100000_add_mcp_server_plugin_kind.sql` gave `assistant.plugins` a `kind` column and the
storage an MCP-backed row needs. It committed to exactly one client-registration mechanism:

```sql
-- Credentials from Dynamic Client Registration (RFC 7591).
ADD COLUMN IF NOT EXISTS oauth_registration_endpoint VARCHAR(1000) NULL,
ADD COLUMN IF NOT EXISTS oauth_client_id VARCHAR(500) NULL,
ADD COLUMN IF NOT EXISTS oauth_client_secret_encrypted TEXT NULL,
```

MCP Authorization 2026-07-28, Overview §3:

> Authorization servers and MCP clients **MAY** support the OAuth 2.0 Dynamic Client Registration
> Protocol (RFC7591). Note that Dynamic Client Registration is **deprecated** and retained for
> backwards compatibility with authorization servers that do not support Client ID Metadata
> Documents.

Cloudflare's MCP v2 post puts a date on it: DCR is *"deprecated for new implementations and is
slated for removal after summer 2027."*

No `kind='mcp'` OAuth client has been written yet — `Infrastructure/OAuth/` holds only
`GoogleWorkspaceOAuthClient`. The cost of changing direction is a migration edit and interfaces
that do not exist yet. After the first `kind='mcp'` row ships against a real server, it is a data
migration plus a re-consent for every affected user.

## 2. Decision

Three registration mechanisms behind one interface, resolved in the spec's priority order:

| Rung | Mechanism | When | Storage per plugin row |
|---|---|---|---|
| 1 | **Pre-registered** | Row already carries `oauth_client_id` | client id (+ optional encrypted secret) |
| 2 | **CIMD** | AS advertises `client_id_metadata_document_supported` | *nothing* — `client_id` is a WarpTalk constant |
| 3 | **DCR** | AS advertises `registration_endpoint` | client id + encrypted secret from `/register` |
| 4 | **Fail loudly** | none of the above | — |

Rung 4 is a task, not an omission. Every dead-end failure mode in Claude Code's MCP OAuth
(`anthropics/claude-code#26675`, `#67258`, `#76075`) is the same bug: a ladder that hard-throws
`Incompatible auth server: does not support dynamic client registration` at the *status* call,
before the user is ever offered a way out.

## 3. Two design findings from reading the code

### 3.1 The per-plugin callback URL breaks CIMD, and the "INSERT, not deploy" goal

`AssistantPluginsController` exposes the callback as
`/api/v1/assistant/plugins/{pluginKey}/oauth/callback`. A CIMD document must enumerate its
`redirect_uris`, and the AS validates the authorization request against that list exactly. With a
per-plugin path, **adding a plugin row would require editing the CIMD document** — which defeats
the migration's stated goal ("adding an app becomes an INSERT") and is made worse by CIMD caching
(§4.3).

Fix: `kind='mcp'` uses one fixed callback for all MCP plugins:

```
/api/v1/assistant/plugins/mcp/oauth/callback
```

This costs nothing, because `DataProtectionPluginOAuthStateProtector` already protects
`{UserId, PluginKey}` in `state` — the plugin key is already carried through the round trip. The
CIMD `redirect_uris` array then has exactly one entry, permanently. `kind='native'` keeps its
existing per-plugin callback unchanged.

### 3.2 Declaring only `private_key_jwt` would hard-fail on the largest CIMD surface

This is the answer to "CIMD forces us to be a public client", and it is a partial answer. From
`negotiateCimdTokenEndpointAuthMethod`:

```ts
if (preferredMethod !== undefined && SHARED_SECRET_TOKEN_ENDPOINT_AUTH_METHODS.has(preferredMethod)) {
  throw new Error(`CIMD clients cannot use symmetric token endpoint authentication method: ${preferredMethod}`);
}
const acceptedMethods = server.tokenEndpointAuthMethods.filter(
  (method) => !SHARED_SECRET_TOKEN_ENDPOINT_AUTH_METHODS.has(method)
);
return negotiateTokenEndpointAuthMethod({ acceptedMethods, defaultMethod: 'none', ... });
```

`client_secret_basic` / `client_secret_post` / `client_secret_jwt` are rejected outright for a
CIMD client — a hard error, not a downgrade. A shared secret is structurally impossible: the
document is public, and `resolveClientIdMetadataDocument` rejects any document containing
`client_secret`, `client_secret_expires_at`, or private JWK material.

`private_key_jwt` survives the filter. But Cloudflare's own default server capabilities are
`['client_secret_basic', 'client_secret_post', 'none']`, so after filtering symmetric methods a
default-configured Cloudflare AS accepts **only `none`**. A document advertising
`token_endpoint_auth_methods_supported: ["private_key_jwt"]` alone throws — failing against every
default Cloudflare-backed MCP server, the largest population of CIMD-capable servers today.

**Decision: advertise both, strongest first, and let negotiation choose.**

```json
"token_endpoint_auth_method": "private_key_jwt",
"token_endpoint_auth_methods_supported": ["private_key_jwt", "none"],
"token_endpoint_auth_signing_alg": "ES256",
"jwks_uri": "https://<public-host>/oauth/client-metadata/jwks.json"
```

`validateChoiceConsistency` requires `token_endpoint_auth_method` to appear inside
`token_endpoint_auth_methods_supported`, so the pair above is the only valid spelling of "prefer
private_key_jwt, accept none".

### 3.3 Honest residual risk of the `none` fallback

On most servers today the negotiated method will be `none`. That is not fully mitigable, and this
plan should not pretend otherwise. What makes it acceptable for WarpTalk specifically — and what
does **not** transfer from the CLI clients whose CIMD bugs prompted this review:

- WarpTalk's `redirect_uri` is a single HTTPS URL on a host it controls via DNS and TLS. The
  localhost-impersonation attack the MCP spec warns about needs an attacker to bind a port and
  receive the code. Nobody else can receive a redirect to WarpTalk's HTTPS callback. This is the
  actual security boundary, and it is stronger than a client secret against the same attack.
- PKCE `S256` is a spec **MUST** and already required of the client.
- `state` is already integrity-protected (`DataProtectionPluginOAuthStateProtector`).
- RFC 9207 `iss` validation is added by T069 and closes authorization-server mix-up.

What must not happen is a silent downgrade nobody can see. T063 persists the negotiated method per
row so a `none` connection is a recorded fact.

`FR-565-005` currently reads "MUST encrypt OAuth credentials at rest". For a CIMD row there is no
client secret to encrypt. T074 amends the requirement text rather than leaving it silently false.

## 4. CIMD contract WarpTalk must satisfy

Mirrored from `validateClientIdentifierUrl` + `resolveClientIdMetadataDocument`. Every rule below
is enforced by at least one shipped AS, so violating any of them is a silent production failure.

### 4.1 The Client Identifier URL

- absolute `https://`, no whitespace, no control characters, no backslash
- no userinfo, no fragment
- **MUST have a path component** (a bare origin is rejected)
- no `.` or `..` path segments — checked against the raw string, not the WHATWG-normalized path
- percent-encoding must decode

Chosen value: `https://<public-host>/oauth/client-metadata/v1.json`

The `/v1` segment is deliberate — see §4.3.

### 4.2 The document

```json
{
  "client_id": "https://<public-host>/oauth/client-metadata/v1.json",
  "client_name": "WarpTalk",
  "client_uri": "https://<public-host>",
  "logo_uri": "https://<public-host>/brand/warptalk-192.png",
  "policy_uri": "https://<public-host>/legal/privacy",
  "tos_uri": "https://<public-host>/legal/terms",
  "contacts": ["<support mailbox>"],
  "redirect_uris": ["https://<public-host>/api/v1/assistant/plugins/mcp/oauth/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "private_key_jwt",
  "token_endpoint_auth_methods_supported": ["private_key_jwt", "none"],
  "token_endpoint_auth_signing_alg": "ES256",
  "jwks_uri": "https://<public-host>/oauth/client-metadata/jwks.json"
}
```

Hard requirements:

- `client_id` **byte-identical** to the URL it is served from
- `client_name` non-empty, `redirect_uris` non-empty
- **MUST NOT** contain `client_secret` or `client_secret_expires_at`
- **MUST NOT** inline private JWK material (`d`, `p`, `q`, `dp`, `dq`, `qi`, `oth`, `k`)
- ≤ **5 KB**, served within a **10 s** timeout
- `grant_types` / `response_types` are intersected with the server's, and
  `authorization_code` ⇔ `code` must be registered together

`policy_uri`, `tos_uri`, `logo_uri`, `contacts` are not decoration — `pickDisplayMetadata` carries
them into the consent screen, and they are the difference between a named application and an
anonymous URL when an AS operator decides whether to trust an unknown domain (§6, Threat 1).

### 4.3 Caching, and why the URL is versioned

`cacheTtlSeconds` reads `s-maxage` first, then `max-age`, caps at **7 days**, and stores nothing
when the response carries `no-cache`, `no-store`, or `private`.

- Serve the document with `Cache-Control: public, max-age=300`. Editing it then propagates in
  minutes, not a week. The cost is one small fetch per authorize on cold caches.
- Never make a breaking change in place. Adding a redirect URI or changing the auth method is a
  **new document at `/v2.json`**, i.e. a new client identity, because in-flight authorizations and
  cached copies will still be validating against the old one.

## 5. Schema changes

Amend the existing migration's comment (it currently attributes the credential columns to DCR
alone) and add a new migration:

```sql
-- 20260904xxxxxx_add_mcp_client_registration_source.sql
ALTER TABLE assistant.plugins
    ADD COLUMN IF NOT EXISTS oauth_client_source VARCHAR(20) NOT NULL DEFAULT 'unresolved',
    -- Cached from AS metadata so the ladder does not re-walk discovery on every connect.
    ADD COLUMN IF NOT EXISTS oauth_cimd_supported BOOLEAN NULL,
    ADD COLUMN IF NOT EXISTS oauth_iss_parameter_supported BOOLEAN NULL,
    -- The method actually negotiated. Null until the first successful token request.
    ADD COLUMN IF NOT EXISTS oauth_token_endpoint_auth_method VARCHAR(40) NULL;

ALTER TABLE assistant.plugins
    ADD CONSTRAINT plugins_oauth_client_source_check
    CHECK (oauth_client_source IN ('unresolved', 'preregistered', 'cimd', 'dcr'));

-- A pre-registered row with no client id is unusable; fail at the boundary, not at connect time.
ALTER TABLE assistant.plugins
    ADD CONSTRAINT plugins_preregistered_requires_client_id
    CHECK (oauth_client_source <> 'preregistered' OR oauth_client_id IS NOT NULL);

-- Mirrors the CIMD rule that a metadata-document client can never hold a shared secret.
ALTER TABLE assistant.plugins
    ADD CONSTRAINT plugins_cimd_forbids_client_secret
    CHECK (oauth_client_source <> 'cimd' OR oauth_client_secret_encrypted IS NULL);
```

`oauth_client_source` is the field whose absence produced `anthropics/claude-code#67258`: a row
that already had a usable client id still fell into DCR and died, because nothing recorded which
mechanism the row had settled on.

## 6. How each Threat from the SWOT is resolved

| Threat | Resolution | Task |
|---|---|---|
| **Domain allowlist / trust policy rejects an unknown capstone domain.** Spec grants the AS this right explicitly. | Not preventable — made survivable. Rung 1 is the escape hatch: an operator registers an app by hand, sets `oauth_client_source='preregistered'` + `oauth_client_id`, and that row works with **zero code change**. Separately, ship the full display metadata in §4.2 so the consent screen shows a named, contactable application rather than a bare URL. | T067, T066 |
| **Ecosystem uneven** — FastMCP has no CIMD (`PrefectHQ/fastmcp#2863`), MCP Python SDK has client-side only (`modelcontextprotocol/python-sdk#1801`), GitLab unshipped. | The ladder resolves it by construction. Detection is per-AS via `client_id_metadata_document_supported`, cached in `oauth_cimd_supported`. Falling through a rung is normal control flow, never an exception. | T065, T067 |
| **DCR removal after summer 2027.** | DCR is one implementation of `IMcpClientRegistrar`, not a branch inside the OAuth client — deleting it is deleting a class and a DI line. Every rung-3 resolution emits a structured `mcp_client_registration_deprecated_path` log with the plugin key, so before the deadline you can enumerate exactly which rows still depend on it. | T067 |
| **Silent downgrade to `none`.** | `oauth_token_endpoint_auth_method` persists what was actually negotiated; the plugin detail response carries it. | T063, T069 |
| **Stale CIMD, up to 7 days.** | `Cache-Control: public, max-age=300` on our own document, plus a versioned URL so breaking changes are new identities, never edits. | T066 |
| **Dead-end with no user recourse** (the Claude Code failure mode). | New error code `client_registration_unsupported` + the in-chat / settings card, reusing the T051 reconnect-card surface. Never surface a raw exception string. | T070 |

SSRF, which the spec devotes a section to, is a risk borne by the party that **fetches** the
document. WarpTalk is the client here and does not fetch anyone's CIMD, so it carries none of it.
That changes the day WarpTalk exposes its own MCP server — out of scope, noted in §10.

## 7. How to install an MCP server (the demo path)

`spec.md` says the catalog is **data, not code**. Today that data can only arrive by hand-written
SQL, which is not a demonstrable install step. T072 adds one endpoint so "install an MCP app" is an
action someone can perform and show:

```
POST /api/v1/assistant/plugins/catalog        (operator-scoped)

{
  "pluginKey":    "linear",
  "label":        "Linear",
  "description":  "Issues and projects",
  "avatarUrl":    "...",
  "kind":         "mcp",
  "mcpServerUrl": "https://mcp.linear.app/mcp",
  "requiredScopes": ["read", "write"],
  "oauth": {
    "clientSource": "unresolved"
  }
}
```

`clientSource: "unresolved"` is the normal case: discovery runs on first connect, and the ladder
picks CIMD or DCR on its own. Only a server that needs rung 1 requires the operator to supply
`clientId` / `clientSecret` / endpoints in the same payload.

Demoed through the existing Swagger surface (T023) — no new admin UI in this sprint. The full
operator sequence, which is what gets shown:

1. `POST` the catalog row above
2. The plugin appears in `/settings/plugins` for every user — **no deploy, no restart**
3. A user installs it, clicks Connect, consents in the browser
4. On callback, `tools/list` is fetched and cached into `tools_json`
5. The plugin's tools appear in the plugins page tiles, in the `@mention` picker, and in
   WarpBot's tool set for that user

Step 1 is "cách cài MCP"; steps 2 and 5 are the demo.

## 10. Non-goals

- **`tools_manifest_hash` drift handling.** The columns stay provisioned. When it is built, its
  only job is to record that a server changed its tool set — a `PluginToolAudit` row. It has
  nothing to invalidate: approval is workspace-level only (§0), and an escalated tool is already
  caught at execution time by the T038 write-confirmation gate. Together with the background
  re-sync that would trigger it, this is the next sprint. Note that `plugins` is a global catalog
  and installs are personal, so re-sync is **one job per plugin row**, not per workspace or user.
- **WarpTalk as an MCP server / authorization server.** The SSRF, trust-policy, and metadata-cache
  obligations in the spec's CIMD security section land on the fetching party. They become ours
  only on that day.
- **Migrating `google_workspace` off `kind='native'`.** Google has no official remote MCP server
  for Drive/Calendar, which is the documented reason the bespoke client exists.
- **An admin UI for the catalog.** T072's endpoint plus Swagger is the operator surface this
  sprint.

## 11. Open risks

- **A public HTTPS host is a hard prerequisite for rung 2.** An external AS must be able to fetch
  our metadata document, and `appsettings.json` currently knows only
  `http://localhost:5200/...`. Rungs 1, 3 and 4 are testable locally; rung 2 is not testable at
  all without it. Secure the host before the sprint starts, not during T073.
- **T055's Docker build blocker is unresolved** (NuGet truncation on `Grpc.Tools.2.60.0`). It sits
  directly in front of the item above.
- **The signing key is a new operational object** with different requirements from the Data
  Protection key ring — it must be published, survive restarts, and rotate with overlapping `kid`s.
- **The CIMD draft is at revision 00** and may change. The versioned document URL (§4.3) is what
  makes a spec change a `/v2.json` rather than a breaking edit.

## 12. Decision record

### D1 — JWT handling: hand-rolled JWS vs `Microsoft.IdentityModel` — **resolved 2026-09-03, use IdentityModel**

**Raised during T068.** `private_key_jwt` needs a signed client assertion. Infrastructure had no
JWT package, so the first implementation assembled the JWS by hand: ES256 over P-256 is a
fixed-width r‖s concatenation, which `ECDsa.SignData(..., DSASignatureFormat.IeeeP1363FixedFieldConcatenation)`
produces directly, and `System.Buffers.Text.Base64Url` is BCL in .NET 10. That kept Infrastructure
free of the auth stack and avoided pinning a version against the one
`Microsoft.AspNetCore.Authentication.JwtBearer` resolves.

**Two facts changed the answer.**

1. The premise "Infrastructure has no IdentityModel" was wrong in substance. `dotnet list package
   --include-transitive` shows `Microsoft.IdentityModel.Tokens 8.17.0` and
   `Microsoft.IdentityModel.JsonWebTokens 8.17.0` already resolved into the API project via
   JwtBearer 10.0.5. Referencing it explicitly adds a declaration, not a binary.
2. The scope that made hand-rolling safe does not hold. Hand-rolled signing is defensible because
   the dangerous half of JWT - algorithm confusion, `alg: none`, key resolution, audience and
   clock-skew checks - lives in *verification*. But this service will also **validate** the OIDC
   `id_token` an authorization server returns during connect, so that a user's provider identity
   comes out of the token they just consented to rather than costing them a second sign-in round
   trip. Validation must never be hand-rolled, and running one library for signing while
   hand-rolling nothing else is simpler than running two mechanisms.

**Resolution.** `Microsoft.IdentityModel.JsonWebTokens` is referenced explicitly from
`WarpTalk.AssistantService.Infrastructure`, **pinned to 8.17.0** to match what JwtBearer already
resolves - IdentityModel has had breaking changes across major versions, and an unpinned reference
becomes a silently-resolved diamond. `ConfigurationMcpClientSigningKeyStore` uses
`JsonWebTokenHandler.CreateToken` for the assertion and `JsonWebKeyConverter` for the JWKS entries.

**Evidence the swap was behaviour-preserving.** `McpClientSigningKeyStoreTests` was written against
the hand-rolled implementation and verifies the output the way a server would - decode the three
segments, rebuild the public key from the published JWK, verify the signature over the literal
signing input. All five tests passed unchanged against the IdentityModel implementation, so the
wire format is identical. Keep those tests pointed at the public behaviour rather than the library:
they are what makes this decision reversible.

**Standing rule this establishes.** Never hand-roll JWT *validation* in this codebase. Signing
alone may be hand-rolled if a future context genuinely cannot take the dependency, but the moment
verification is involved, use the library.
